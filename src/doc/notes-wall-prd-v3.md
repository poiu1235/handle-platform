## 一、产品定位

### 1.1 它是什么

一张**时间线形态的随手贴板**。用户在任何瞬间想到什么、怕忘什么，记一笔就走；
板子自己负责把「急事」推到眼前、把「过期的事」悄悄收走、把「念头」沉淀成一条
可以一直往下翻的历史。

它对标的不是日历、不是任务管理工具，而是**口袋里那本便利贴**：写的时候零决策
成本（不用想优先级、不用排期），看的时候一眼知道什么还热着、什么已经凉了。

### 1.2 它明确不做什么（负面清单）

以下形态**刻意不做**，是定位边界，不是功能缺失：

- **不是日历**：没有时刻粒度，没有「几点几分」，只有日期；
- **不是任务拆解**：不提供步骤、子项、进度；
- **不是 todo list**：没有「下一步做什么」的顺序语义，主时间线只讲创建时间；
- **不是长任务**：「这周采买一大批物资」这类跨周期的事不该记在这里；
- **不是周期任务**：没有重复规则（每天背单词这类需求本产品不承接）；
- **不主动打扰**：无推送、无系统通知、无提示音、无弹窗、无「该完成了」的提醒。

### 1.3 「不加压力，但留一个提醒」怎么落地

提醒完全由**三层视觉**承担，层层加深、永不主动打断：

1. **倒计时角标**（还剩 N 天 / 明天到期）——事还远，扫一眼即可；
2. **「今天到期」强调**（截止日当天，建议配底色/描边加重）——今天必须看一眼；
3. **已过期域**（置灰 + 按快被收走的排最前）——过了的事集中在一个折叠域里，
   用户哪天想起来「我是不是忘了什么」，点开就能找到，而不是混在主线里瞎。

已过期域存在的意义正是用户原话：**「有可能用户真的忘记做了什么事，他会在已过期
的分类里看一下；但已完成里的就完全没有必要去看了」**——所以过期和完成必须是
两个独立的域。

## 二、两类内容：灵感 与 备忘

### 2.1 灵感（idea）

- 例：「做一个便利贴页面」。
- 无日期概念、无完成概念、无流转。
- 动作只有两个：**删除**、**Pin**。
- 生命周期：进入主时间线后**永远留在历史里**，可以无限下翻；直到被手动删除。
- 定位是长期沉淀的念头流水，不是临时数据——不参与任何自动清理（条数上限见 8.2）。

### 2.2 备忘（memo）

- 例：「冰箱鸡蛋没了，买鸡蛋」「星期天提醒我和王星的聚餐」。
- 可选设一个截止日期（今天 ~ 今天+7）；不设则系统按创建日 + 7 天兜底。
- 有完整生命周期：**正常 → 已过期 → 已完成 → 自动清除**（见 三）。
- 动作：**完成**（正常期/过期期均可）、**删除**、**Pin**、**编辑**（仅正常期）。

### 2.3 对比

| | 灵感 idea | 备忘 memo |
| --- | --- | --- |
| 日期/倒计时 | 无 | 可选，最多今天+7 |
| 「完成」 | ❌ 没有 | ✅ 任意阶段（正常/过期）可手动完成 |
| 自动流转 | ❌ 不参与 | ✅ 过期 → 归档 → 清除 |
| 历史长度 | 无限下翻 | 最长约 14 天离场，归档后 30 天清除 |
| 动作 | 删除 / Pin | 完成 / 删除 / Pin / 编辑 |
| 样式 | 白卡（建议沿用描边白卡） | 强调色卡 + 倒计时角标 |

## 三、备忘的时间规则（核心机制）

### 3.1 口径

- 一切按**自然日**计算，跨零点即换天；没有时刻、没有小时。
- 截止日：用户设的日期，或未设时的 `创建日 + 7 天`。
- 日期选择范围：**今天 ~ 今天 + 7**，超出不可选（D1 的「7 天最大期限」）。

### 3.2 生命周期四态与流转时刻表

| 阶段 | 时间区间 | 归属分区 | 显示 |
| --- | --- | --- | --- |
| 正常 | 创建日 ~ 截止日（**含截止日当天**） | 主时间线（或 Pin 区） | 有日期：还剩 N 天 / 明天到期 / **今天到期**（强调）；无日期：无倒计时角标 |
| 已过期 | 截止日次日 00:00 起，滞留 **7 天** | 已过期折叠域 | 置灰 +「已过期 N 天」徽标（N = 今天 − 截止日，1~7） |
| 自动归档 | 截止日 **+ 8 天的 00:00**（过期满 7 天） | 已完成折叠域 | 划线置灰 + 标识「超期自动归档」 |
| 清除 | 进入已完成时刻 **+ 30 天** | 消失（不可恢复） | — |

手动路径贯穿全程：正常期或过期期**任意时刻点完成** → 立即进入已完成、标识
「手动完成」，30 天后清除；**任意时刻可删除**（二次确认）。

### 3.3 示例（9月1日创建、从未手动处理）

- **未设日期**：9/1–9/7 正常（无角标）→ 9/8 截止日「今天到期」→ 9/9–9/15 已过期
  （9/15「已过期 7 天」排在已过期域最前）→ **9/16 00:00 自动转已完成** →
  **10/16 00:00 静默清除**。
- **设了 9月5日**：9/1「还剩 4 天」→ … → 9/4「明天到期」→ 9/5「今天到期」→
  9/6–9/12 已过期 → **9/13 00:00 自动转已完成** → **10/13 00:00 清除**。

> 「7 + 7 ≈ 14 天周期」为口径表述；精确时刻以 3.2 规则表为准（截止日后第 8 天
> 00:00 归档）。

### 3.4 明确不做提示

过期不弹提示、不补通知、不问「完成了吗」——**设计初衷就是不想让用户回来点完成**。
忘了的事由已过期域承接（它自己会排到最前面等你），处理完了的事自动消失，
两端都不需要用户勤快。

## 四、页面结构与四大分区

页面自上而下四个分区；**任一条目在同一时刻有且只有一个归属**：

| 条目状态 | Pin 区 | 主时间线 | 已过期域 | 已完成域 |
| --- | :-: | :-: | :-: | :-: |
| 正常 + 已 Pin | ✅ | | | |
| 正常 + 未 Pin | | ✅ | | |
| 已过期（无论是否 Pin 过） | | | ✅ | |
| 已完成（手动或自动） | | | | ✅ |

分区之上有一条**工具行**：左侧类型筛选分段「全部 / 仅备忘 / 仅灵感」（纯前端
过滤、切换零请求）——「仅灵感」时已过期 / 已完成域（纯备忘域）自然清空、整区
隐藏；右侧「列表 / 日历」展示切换（对照会员页展示模式，默认列表，见 4.5）。
工具行下方另有**搜索框**（仅列表视图，纯前端过滤，见 4.6；2026-09-13 新增）。
**段按钮兼作排序开关**（2026-09-12 用户裁定）：第一下进入筛选并即按字段排序，
再点一下反向——**仅备忘**：四个备忘模块（Pin / 正常 / 已过期 / 已完成）各自按
截止日排序（今天到期 → 明天 → 还剩 N 天……），方向由近到远（↑）⇄ 由远到近（↓）
循环；**仅灵感**：灵感模块（Pin / 时间线）按创建时间从新到旧 ⇄ 从旧到新。
**无日期备忘有时效（创建日 + 7）**：按派生截止日自然参与排序与超期流转（过期后
同样进已过期域、带「已过期 N 天」徽标）；排序只作用于备忘模块——Pin 区与时间线
在「全部」视图保持创建倒序、已过期域「全部」视图保持「快被收走最前」。

### 4.1 Pin 区

- 页面最顶部独立分区，**默认展开，可手动折叠**（建议记忆折叠状态）；分区容器用
  **品牌蓝浅底面板**强调（四分区中唯一带色块容器，2026-09-12 用户裁定，样式稿定）。
- 收纳所有处于**正常态**的置顶条目（灵感 + 备忘混排，按创建时间倒序）。
- **不豁免流转**：置顶备忘到期后照常离开 Pin 区进入已过期域——Pin 的语义是
  「排在最前面给我看」，不是「免于系统整理」。
- 空时整区隐藏，不留空标题。

### 4.2 主时间线

- 灵感 + 备忘混排，**创建时间倒序**，最新在最上面（D12）。
- 位置与紧急程度解耦：一条三天前创建、明天到期的备忘，就排在昨天创建的灵感
  下面——紧迫感由倒计时角标和「今天到期」强调表达，不靠排序。
- 时间线的自然形态：**顶部约 7 天内是灵感与备忘混排；越往下备忘越少**（14 天内
  必然离场）；**底部是纯灵感历史，无限下翻**。
- 已过期、已完成条目不出现在主时间线（进了各自的折叠域）。

### 4.3 已过期折叠域

- 主时间线之后的一条折叠栏（建议样式「已过期 N ▾」），默认收起。
- 收纳所有已过期未处理、未被手动完成的备忘；**置灰显示**，徽标「已过期 N 天」。
- **排序：距自动归档还剩多久升序**——已过期天数最多的（马上要被收走的）排最前。
  打开一看，最先看到的就是「再不看就没啦」的内容，提醒效果最强。
- 条目动作：**转为已完成**（记「手动完成」）、**删除**。
- 这是用户「回头看看有没有真忘了什么事」的窗口，独立于已完成域存在。

### 4.4 已完成折叠域

- 默认**折叠**、可点击展开（D10）。
- 收纳手动完成的 + 超期自动归档的备忘；划线置灰。
- 域内排序：按进入已完成的时间倒序（最近处理的在上）。
- 每条带来源标识：**「手动完成」/「超期自动归档」**，仅此两类——在哪个阶段点的
  完成不做区分，以用户处理结果为准。
- 进入后再过 30 天**静默清除**（无通知、无确认）；清除前不占用户注意力
  （默认折叠），清除后不留痕。
- 条目动作：**删除**——不提供恢复（见 9.1）。

### 4.5 日历视图（2026-09-12 新增）

- 工具行右侧「列表 / 日历」切换（对照会员页展示模式分段控件），默认列表。
- 月历（周一起，‹ › 翻月 + 「今天」回本月）：只展示**当前月**的条目——备忘按
  **截止日**落位（仅正常态；灵感按**创建日**落位，无过期概念全部展示，
  2026-09-12 用户裁定灵感也进日历）。已过期 / 已完成备忘不进日历；无日期备忘
  落在派生截止日（创建日 + 7）上。
- 条样式区分类型：备忘黄条 / 灵感白条描边（同卡片体系）；置顶条带 📌 前缀。
- **格内 >5 条折叠**（2026-09-12 用户裁定）：显示前 4 条 + 「剩下 +x 个」，点开
  悬浮列表查看剩余条目，点列表中的条目进入只读弹层。
- **点击日历条目 = 只读弹层**（2026-09-12 用户裁定，不再跳回列表）：弹层仅展示
  全文与状态徽标 / 截止日等 meta，**不具备删除和修改**（修改回列表展开卡片操作），
  参考会员页详情弹层。
- **切换月即重新拉取**：全量口径下月份过滤在前端派生，翻月 / 回今天触发一次
  loadNotes（顺带吸收他端变更）。类型筛选与日历叠加生效（「仅备忘」日历只剩
  黄条、「仅灵感」只剩白条）。

### 4.6 搜索（2026-09-13 新增）

- 入口：**列表视图工具行下方的搜索框，固定宽度与类型筛选段无箭头默认态同宽
  （208px，不随激活排序箭头变宽；2026-09-13 用户裁定）**；日历视图不显示——
  搜索是列表的查找能力，不影响日历落位；查询词在切走再切回后保留。
  `type="search"`，原生清除。
- **纯前端过滤，切换零请求**：全量拉取（≤500 行）架构下「即搜」——查询词与
  content 双侧先**归一化**（去全部空白，含全角空格 / NBSP / 换行）再比大小写
  不敏感子串——中文按子串命中不分词；混排英文时大小写差异、手滑多打的空格都
  不会漏；API 契约（8.3）与数据库**零改动**，无需全文检索。
- **叠加生效**：搜索在类型筛选（全部 / 仅备忘 / 仅灵感）之后过滤。
- **平铺结果**：分区是浏览结构、搜索是查找结构——有查询词时不渲染四分区，
  渲染一个平铺结果列表（置顶 / 主时间线 / 已过期 / 已完成**四域统一搜索**，
  找回旧东西是主场景），创建时间倒序，上方计数行「找到 N 条含…」，命中片段
  品牌蓝 `<mark>` 高亮（黄备忘 / 白灵感 / 灰失效三种卡底通吃；命中可跨越原文
  中的空格 / 换行，高亮段按原文原样渲染）；清空查询词
  即回四分区。空结果独立空态文案。
- 量级边界：500 条上限（9.2-6）内为亚毫秒过滤、毫秒渲染。若未来大幅上调
  上限至数千条，瓶颈先出现在**全量拉取体积与全量渲染**（非搜索本身）——届时
  一并做 分页拉取 + 渲染虚拟化 + 搜索下推（PostgREST `content=ilike.*q*`，
  中文子串 `ilike` 足够，无需分词/全文索引），本节的「纯前端」契约随之作废
  重写。

## 六、布局：普通双列 grid（非瀑布流）

### 6.1 为什么不用严格瀑布流

按高度自动平衡的真瀑布流会把卡片填进「最短的一列」，两列进度不一致后，
**新条目可能出现在旧条目下面、甚至更靠上**——直接破坏「越靠上 = 越新」这条
本产品的第一直觉。时间线可读性 > 视觉参差感，故弃用（D13）。

### 6.2 填充规则

- **普通 grid 逐行从左到右顺序填充**：第 1、2 条在第一行，第 3、4 条在第二行……
  阅读顺序与创建顺序严格一致（之字形）。
- **移动端固定 2 列**；PC 端随容器宽度增加列数（断点已按样式稿定：≥1080px 4 列 /
  760–1079px 3 列 / ≤759px 2 列）。面板宽度对齐导入页口径
  `max(100vw×2/3, 560px)`（2026-09-12 用户裁定，CSS 直接复用 `--bd-import-col`）。
- 同一行卡片**等高拉伸**：行高 = 行内最高的卡，卡内 meta 沉底，行缘整齐
  （2026-09-12 用户裁定，样式稿已实现）；仍**不做跨行填充**。
- 已过期域、已完成域展开后用同样的 grid 规则。

## 八、数据与实现：状态全派生，无需定时任务

### 8.1 表结构（`supabase/notes.sql`，风格对照 `supabase/cards.sql`；Supabase SQL Editor 整体执行一次）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid pk | `gen_random_uuid()` |
| user_id | uuid → auth.users | `on delete cascade`；RLS 归属键 |
| kind | text not null | `'idea' \| 'memo'`；**创建后不可变更**——CF 层 PATCH 白名单不含 kind + `notes_kind_lock` 触发器钉死（D15） |
| content | text not null | 1–500 字、非空白；CF 层 JS trim 全部 Unicode 空白，DB CHECK 兜底 ASCII trim（与 `cards_name_trimmed` 同款分层，写入路径强制等级对齐） |
| due_date | date null | 仅 memo；null = 未设日期（截止 = 创建日 + 7 兜底，界面不显示倒计时，D5）。窗口 [今天, 今天+7] 是移动窗口且按客户端本地日历——DB 判不了「今天」（current_date 是 UTC），CF 层校验（请求携带 `today`，同 cards 预留 #8 口径），DB 不设窗口约束 |
| finished_at | timestamptz null | 仅 memo；手动完成时刻 = 用户处理结果（正常期 / 过期期点完成统一写它，D10）。**自动归档不写库**（时间派生）；一经写入不可改值、不可清除、不得超前 5 分钟（`notes_finish_lock` 触发器） |
| pinned | boolean default false | 置顶（D11：只影响 Pin 区收录，不豁免流转） |
| created_at / updated_at | timestamptz | updated_at 由 `moddatetime` 触发器维护；冲突 = 后写覆盖先写（LWW，与 cards 同口径） |

- `notes_idea_plain` CHECK：`kind='idea' ⇒ due_date 与 finished_at 均为 null`——
  灵感是裸内容（D3），一个约束钉死两个不变式，含绕过 CF 的直写兜底；
- **无唯一键**（同一句话允许记两条）、**无流水表**；RLS 四策略 +
  `grant select, insert, update, delete to authenticated`（与 cards 第 3 节同构）；
- 索引仅 `notes_user_list (user_id, created_at desc)`——没有 cron / 结算 / 服务端
  提醒，DB 之外没人按时间找行；
- 触发器三枚：`moddatetime`、`notes_kind_lock`（D15）、`notes_finish_lock`（D10：
  已完成只可删除——content / due_date / pinned / finished_at 一律冻结）；
- 与 v2 便签墙的 notes 表草案（notes-wall-prd-v2.md 第六章：kind=task/idea、
  remind_at、repeat_rule、last_fired_at 等）完全无关，该草案**从未建库**；本文件
  为全新建表，**无迁移段**。

### 8.2 派生规则（全部由时间算出，不写库；客户端本地日历，SQL 文件头同口径）

```
截止日       = due_date ?? (created_at 本地日 + 7 天)
正常         = 今天 ≤ 截止日 且 无 finished_at 且 未到归档时刻
已过期       = 截止日 < 今天 < 归档时刻
归档时刻     = 截止日 + 8 天 00:00
已完成(自动) = now ≥ 归档时刻 且 无 finished_at    → 标识「超期自动归档」
已完成(手动) = finished_at ≠ null                  → 标识「手动完成」
清除时刻     = (归档时刻 或 finished_at) + 30 天
```

- **唯一需要写库的状态动作是手动完成**（写 `finished_at`）；过期、归档、清除全部
  由时间派生，前端在 进站 / 轮询 / 回焦 / 跨零点 时重算即可，**无需服务端 cron、
  无结算 RPC、无状态机写放大**——时间自己会流动，不写库的状态才不会烂（沿用
  v2 的派生哲学）。对照 cards：v3 没有 settle / import RPC 的必要，DB 只剩 CRUD。
- 已过清除时刻的条目：读路径直接过滤不展示（见 8.5 清理）。

### 8.3 API 契约（functions/api/notes.js + notes/[id].js）

沿用 cards 中间层模式：`_middleware.js` 已验签并把 access token 放进 `data`，
本层只做白名单 / 枚举 / 窗口校验，RLS 兜底数据归属。

| 方法 | 路径 | 语义 | 返回 |
| --- | --- | --- | --- |
| GET | `/api/notes` | 全量拉取（≤500 行，`order=created_at.desc`；分区 / 排序 / 状态全在前端派生，切换零请求） | 行数组 |
| POST | `/api/notes` | 新建（kind / content / due_date?；pinned 恒从 false 起——先上板再钉） | 201 单行 |
| PATCH | `/api/notes/:id` | **diff-only** 部分更新（content / due_date / pinned / finished_at） | 单行 |
| DELETE | `/api/notes/:id` | 删除（任意状态可用；二次确认在前端） | 204 |

- **POST**：kind 枚举；content 1–500 trim；due_date 仅 memo（idea 携带 → 400），
  ISO 日期且须落在 [today, today+7]（`today` = 客户端本地日期，非法回退服务器
  日期——伪造仅自伤）；容量：**贴上限时先顺手清理再复数**（见 8.5 服务端通道），
  复数后仍 ≥ 500 → 409（HEAD `Prefer: count=exact`）。
- **PATCH 规则按派生态收紧**（客户端携带 `today` 供判定）：
  - 正常态：content / due_date / pinned / finished_at 均可（due_date 清空显式传
    null = 改回未设日期；due_date 与新建同一套窗口，含下界 ≥ today，评审
    2026-09-12 #3）；
  - 已过期：仅 `finished_at`（转为已完成）可用；content / due_date / pinned →
    400「已过期不可编辑 / 不可改期复活」（9.1-11）；
  - 已完成：拒绝一切 PATCH（只可删除，9.1-10；DB 触发器兜底）；
  - `finished_at` 由客户端写 `new Date().toISOString()`，CF 校验 ≤ now + 5min
    （时钟漂移容忍；超前更多 → 400）。
- **diff-only 提交契约沿用 cards**：只传变化字段，未携带字段保留现值；「清空」
  必须显式传 null，禁止用缺省表达清空；`updated_at` 触发器维护，冲突 LWW。

### 8.4 校验分层（CF 层 400 / DB 层兜底，对照 cards-db 7.x）

| 不变式 | CF 层 | DB 层 |
| --- | --- | --- |
| kind 枚举 | ✅ | CHECK |
| 灵感无日期、无完成 | ✅ | `notes_idea_plain` CHECK |
| content 1–500 + 非空白 + trim | ✅ JS trim | CHECK（ASCII trim 兜底） |
| due_date ∈ [today, today+7] | ✅（payload.today） | —（DB 无「今天」） |
| 过期后不可改期复活 | ✅（today 判定） | — |
| kind 不可互转 | ✅ 白名单不含 kind | `notes_kind_lock` 触发器 |
| 已完成只可删除 | ✅ 派生态判定 | `notes_finish_lock` 触发器 |
| finished_at 不可改 / 清 / 超前 | ✅ ≤ now+5min | `notes_finish_lock` 触发器 |
| 每用户 ≤ 500 | ✅ POST 前 count → 409 | — |

**纵深取舍（评审 2026-09-12 #2，故意的，非遗漏）**：

- DB 兜底的是**不需要知道「今天」的不变式**——kind 枚举、灵感裸内容、trim、
  kind 锁、完成锁；时间自己会流动的规则才写库；
- CF 层兜底的是**移动窗口 / 派生态**规则——due_date 窗口、过期不可复活、过期
  不可编辑。DB 没有「客户端本地今天」（current_date 是 UTC），精确规则无法落库
  （cards 同款先例：DB 只做 `end ≥ start` 静态不变式，日期窗口全在 CF 层
  `dateWindowError`）；加 ±1 天松弛的粗粒度触发器只会引入新的口径噪音，不做；
- **候补条款**：一旦出现第二条写入路径（离线优先缓存、直连 Supabase SDK），
  上述 CF-only 规则立即失效——届时必须先把这些规则收编为服务端校验或物化
  本地日，再开通该路径，不得直接放开直写。

### 8.5 清理与同步

- **清理（V1 无 cron，双通道）**。清除条件：`finished_at < now() − 30 天`（手动
  行）；`finished_at is null 且 due_date < current_date − 37`（自动有日期行）；
  `finished_at is null 且 due_date is null 且 created_at < now() − 45 天`（无日期
  行；截止 = 本地日 + 7、归档 +8、清除 +30，UTC 近似 ±1 天误差可接受）。
  - **客户端通道**（保证界面即时性）：GET 合入后按本地日历派生清除时刻，对已过
    清除时刻的行批量 DELETE（`id=in.(...)`，幂等、多端任一端触发即可，重复执行
    0 行）；读路径本就过滤，不删除也不展示；
  - **服务端通道**（保证计数口径，评审 2026-09-12 #1）：POST 容量计数达到上限时，
    先按上述条件的 UTC 近似执行一次 DELETE 再复数——没有它，久未打开面板期间
    积累的「僵尸行」会占用 500 额度，造成"没记几条却 409"的错位；未达上限不做
    多余请求（僵尸行无害，任一次 GET / POST 都会顺带清走）。
  V2 收编进 cron-worker 时两通道退役（条件式不变）。
- 多端同步沿用平台现成机制（快照秒开 + 可见时轮询 + 乐观更新 + LWW），本 PRD
  不重述。
- 每用户上限 **500 条**（物理行数；灵感长期沉淀，较旧版 200 放宽）。

### 8.6 联调必测清单

1. idea 携带 due_date / finished_at → 400；绕过 CF 直写 DB → `notes_idea_plain` 拒；
2. PATCH kind → 400（白名单）；绕过 CF 直改 → `notes_kind_lock` 拒；
3. 完成后再改 content / pinned / finished_at → `notes_finish_lock` 拒；DELETE 正常；

5. 过期后 PATCH due_date / content → 400「不可改期复活」；
6. due_date = today+8 → 400 窗口；today 本身合法（立即「今天到期」强调，次日过期）；
7. content 501 字 / 纯空格 → 400；
8. 第 501 条 POST → 409；
9. 跨零点：截止日当天正常 + 「今天到期」，次日 00:00 进已过期域（前端派生断言）；
10. 无日期备忘：创建日 +7 截止、+15 归档、+45 清除（前端派生断言）；
11. 双端并发编辑同一条 → LWW 后写胜；

## 九、边界与裁定记录

### 9.1 已定的边界

1. **截止日当天不算过期**：正常显示 +「今天到期」强调；次日 00:00 才进已过期域。
2. **倒计时为负不显示数字**：置灰进域，绝不出现「已过期 -3 天」。
3. **过期后手动完成 =「手动完成」标识**：不区分在正常期还是过期期点的，以用户
   处理结果为准（用户明确裁定，无需第三种「过期后确认」标识）。
4. **Pin 到期照常流转**：置顶备忘过期后离开 Pin 区进已过期域，Pin 不豁免
   （用户明确裁定，否决了「留在 Pin 区置灰」的方案）。
5. **30 天从进入已完成那一刻起算**：无论当天就点完还是拖满 14 天被收走，
   进域后都有完整的 30 天保留期。
6. **无日期备忘的 7 天是兜底不是倒计时**：界面不显示「还剩 7 天」，避免被误读成
   用户自己设的期限、制造压力。
7. **没有任何到期提示**：连轻量提示都被否决，不打扰是硬约束。
8. **灵感永不过期、不可被完成**：灵感离开系统的唯一方式是手动删除。
9. **类型不可互转**：灵感/备忘创建时定死，编辑不提供类型切换；记错了删掉重记
   （2026-09-12 用户明确裁定，否决互转方案，D15）。
10. **已完成不可恢复**：已完成域定位是「不必再看的归档」，只进不出（仅可删除）
    ——恢复会把归档变回工作集；误完成的成本极低（重记一条）。
11. **已过期不可改日期复活**：改期 = 重新记一条；保住「已过期」语义纯净，
    杜绝靠改日期无限续命的僵尸备忘。
12. **时区口径**：due_date 是纯日期，倒计时与流转按「查看设备的本地今天」派生
    （与 cards 结算 `p_today` 同口径）；跨时区查看无日期备忘时，兜底截止日随
    查看端日历 ±1 天——主查看端即记录者本人设备，接受。
13. **500 上限的并发竞态接受**（评审 2026-09-12 细节 2）：先 count 后 insert 存在
    理论竞态（两请求同时读到 499 → 501）——单用户低频写入，不为此引入事务计数；
    且贴上限时的顺手清理（8.5）已把僵尸行从计数中剔除。
14. **finished_at 无下界接受**（评审 2026-09-12 细节 1）：只校验不超前 5 分钟，
    不校验过去——伪造旧完成时刻仅自伤（提前自己那条的清除日），SQL 注释已声明。

## 十一、后续任务：配图（最多一张）——方案已定，未排期

> 2026-09-13 与用户确认的方向性结论：**可以做**；存储**选 Supabase Storage，
> 明确不用 Cloudflare D1**；检测分两层——技术校验必做，内容审核 V1 不做。
> 本节为实现蓝图（工作量感 3–4 天：迁移 + 上传 UI + 压缩 + 展示 + 清理），
> 排期时按此执行，不重新论证。

### 11.1 数据与约束

- `supabase/notes.sql` 增量段：`alter table public.notes add column image_path text;`
  ——**「最多一张」由单列结构天然保证，零检测代码**；
- CF 层 POST / PATCH 白名单增加该字段（显式传 null = 换图 / 清图，沿用 diff-only
  契约）；灵感 / 备忘都允许带图（`notes_idea_plain` 只管日期与完成，不动）；
- `notes_finish_lock` 触发器冻结清单加 `image_path`——已完成条目连图一起冻结
  （与 content / pinned 同款逻辑）。

### 11.2 存储选型（已裁定）

- **Supabase Storage 私有桶** `note-images`，对象路径 `notes/{user_id}/{uuid}.webp`；
  RLS 策略 `(storage.foldername(name))[1] = auth.uid()::text`——与表 RLS 完全
  同构，权限模型零新增概念；
- 桶配置即第一道检测：allowed MIME = jpeg / png / webp / gif，max file size
  ≈ 5MB——在存储层挡掉越界文件，不依赖业务代码；
- **不用 D1**：D1 是 SQLite 关系库不是对象存储（行大小 / 单语句限制小、二进制
  拖垮备份与导出、无 CDN 缓存与图片处理）；图片元数据就是 notes 表的一列，
  不引入第二个真相源；D1 在本 feature 中没有合理位置；
- Cloudflare 侧的正确替代是 R2（零出口流量费 + 更大免费容量），但需手写
  「验 Supabase JWT → 签 R2 预签名 URL」胶水 + CORS + 独立清理路径——**现在
  不为一张图引入第二套平台**；人均图片量真涨起来后，把存储后端换成 R2 是一次
  性搬运，表结构与 API 形态不变，届时不预付。

### 11.3 上传链路与展示

- 客户端校验（第二道）：MIME 白名单 + 大小上限 + `createImageBitmap` 真解码
  （挡改后缀的伪装文件）；
- **客户端 canvas 重编码**：长边 ≤ 1280px → webp（约 100–300KB）——一石三鸟：
  控制存储成本、卡片渲染快、**剥 EXIF（含 GPS 定位）**（用户拍照直传是隐私
  事故高发点，这道检测最值得做）；
- 上传路径 V1 简单版：客户端把文件 POST 给 CF 函数，函数验签后以 service role
  转传 Storage（链路最少）；量大后换 signed upload URL 直传（省 Workers 带宽），
  函数只负责签发；
- 展示：CF 代理端点 `GET /api/notes/:id/image`（验 token → 302 短时效签名读
  URL，或流式转发 + `Cache-Control: private`）；卡片 `loading="lazy"` + 图片
  **固定 aspect-ratio 框**——grid 行内等高拉伸，图片不定尺寸会把整个网格撑跳；
- 每行多一个 URL 字符串对全量拉取（8.3 GET）体积影响可忽略；真实风险是渲染
  500 个 `<img>`，lazy loading 解决。

### 11.4 检测边界（已裁定）

- **技术校验必做**（11.2 桶配置 + 11.3 客户端校验 / 重编码）；
- **V1 不做 NSFW / 违规内容自动审核**：数据 RLS 严格私有、无分享 / 公开展示面，
  不存在传播，不上审核站得住；**触发条件 = 任何分享 / 公开能力上线前，必须接入
  第三方内容安全 API**——所有上传收口在同一个 CF 函数，届时加一道审核调用即
  改一处，架构上已留好口子。

### 11.5 运维义务

- **孤儿对象**：删 note / 换图时尽力删一次旧 Storage 对象（best-effort）；
  真正的孤儿扫尾与 8.5 的 V2 cron-worker 收编到一起做，不单独排期。
